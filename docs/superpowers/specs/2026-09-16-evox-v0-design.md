# EvoX v0 — Active Lineage Modes

## Purpose

EvoX tests one narrow synthesis of GAx and AnotherOddThing:

> Can evolution preserve several executable procedures that are equally successful on the observations seen so far, can a linear transform of their counterfactual behavior expose distinct computational modes, and can an actively chosen probe select a useful mode for a related task?

The repository begins with a synthetic mechanism test rather than ARC-GEN. The first gate must separate four questions that would otherwise be confounded by a large benchmark: program evolution, behavioral mode extraction, active experiment selection, and reuse of an identified mode.

## Claim boundary

A v0 PASS means only that the complete pipeline works in a controlled program family generated by a small expression grammar. It is not evidence that spectral modes universally correspond to algorithms, that the method solves ARC, or that evolutionary genealogy transfers broadly.

The intended v0 claims are:

1. **Behavioral multiplicity:** evolution can retain several exact- or near-exact-fitting executable programs whose outputs agree on the visible training set but differ on counterfactual inputs.
2. **Mode recovery:** an SVD of counterfactual behavior signatures followed by clustering can separate those programs into stable behavioral modes without using syntax-family labels.
3. **Active identification:** choosing the next input by maximum disagreement between current mode predictions identifies the hidden generating mode with fewer probes than matched random probing.
4. **Mode-conditioned reuse:** after identifying the mode, seeding a related search from programs in that mode reaches the follow-up target with fewer program evaluations than a fresh random population under the same evolutionary machinery.

Every result must report failures and ambiguous cases. No test may infer a mode from program syntax, ancestry labels, or target metadata.

## World

Programs map integer triples `(x0, x1, x2)` to a bounded scalar. Programs are expression trees drawn from a safe grammar:

- terminals: `x0`, `x1`, `x2`, constants `-2`, `-1`, `0`, `1`, `2`;
- unary operation: `neg`;
- binary operations: `add`, `sub`, `mul`;
- all intermediate and final values are clipped to a fixed magnitude to prevent runaway arithmetic.

The initial hidden mechanisms are deliberately simple:

- direct family: `x0`;
- relational family: `x1 * x2`.

Visible training examples obey `x0 = x1 * x2`, so both hidden mechanisms produce identical targets. The evolutionary system therefore cannot distinguish the mechanisms from training fitness alone.

A separate counterfactual probe pool breaks that correlation. It is generated deterministically from a bounded Cartesian grid and excludes points where the two reference mechanisms agree. Probe outputs are never included in evolutionary fitness during the mode-discovery stage.

A follow-up target preserves the identified mechanism while changing an outer transformation, initially `base + 1`. This creates related direct and relational tasks: `x0 + 1` and `x1*x2 + 1`.

## Program evolution

The evolutionary engine is intentionally small and inspectable.

Each individual records:

- unique integer id;
- generation;
- optional parent id;
- expression tree;
- visible-task mean squared error;
- number of tree nodes.

Selection ranks by visible-task error with a small parsimony tie-break. Each generation keeps elites and fills the remaining population with mutated elite descendants. Mutation replaces one subtree with a randomly generated subtree, with deterministic RNG seeds.

The engine records the full individual ledger. This is genealogy evidence, not a source of mode labels.

A viable set consists of the best programs whose visible MSE is below a declared tolerance. Experiments that fail to retain enough viable behavioral diversity are classified as inconclusive for downstream mode claims rather than silently changing thresholds.

## Behavioral representation

For each viable program `p_i` and each counterfactual probe `z_j`, evaluate

`B[i,j] = p_i(z_j)`.

Rows are centered before decomposition. Compute an SVD of the centered behavior matrix and retain the smallest number of singular coordinates explaining at least 95% of nonzero variance, with a minimum of one coordinate.

Cluster the embedded program rows into two modes with deterministic k-means. Cluster ordering is canonicalized by the median prediction on the lexicographically first discriminating probe so labels are stable between runs.

The implementation may compute post-hoc diagnostic labels (`direct-like` versus `relational-like`) only for auditing mode purity. Those labels must not influence SVD, clustering, probe choice, posterior updates, or transfer seeding.

Mode quality metrics:

- effective SVD rank;
- explained variance retained;
- cluster sizes;
- post-hoc purity against reference-family behavior;
- separation between cluster centroids;
- ancestry transition/leakage rate when parent and child are both in the viable set.

## Active probe selection

For each mode, predict the hidden target output at a candidate probe by the median prediction of viable programs assigned to that mode.

Maintain a posterior over the two modes, initialized uniformly. For a candidate probe, compute expected posterior entropy assuming a small fixed Gaussian observation model around each mode prediction. Choose the unused probe with maximum expected information gain. Ties are broken lexicographically.

After the oracle returns the true hidden target output, update the mode posterior with the same likelihood model.

The matched random control receives:

- the same hidden target;
- the same candidate probe pool;
- the same maximum number of probes;
- a deterministic independent random stream.

Primary identification metrics across many trials:

- final mode-identification accuracy;
- mean probes to posterior confidence threshold;
- final posterior entropy;
- fraction of trials remaining inconclusive.

The hidden mode label is used only to score the result after probing.

## Mode-conditioned transfer

After probing, choose the mode with maximum posterior probability. Build a seed population by sampling/mutating viable programs from that mode. Run the same evolutionary engine on the related follow-up task.

Compare with a restart population drawn from the ordinary random program generator. Both conditions receive the same population size, mutation operators, target examples, stopping criterion, and maximum program-evaluation budget.

Primary transfer metrics:

- evaluations until first exact solution;
- success under fixed budget;
- best MSE at budget exhaustion.

A third audit condition seeds from the *wrong* mode. This is essential: if both mode seeds beat restart equally, the advantage is generic warm-starting rather than mode-specific reuse.

## Frozen v0 experiment

The canonical experiment will run a deterministic sweep over multiple RNG seeds and both hidden mechanisms. It records one JSON receipt containing configuration, per-seed results, aggregate metrics, and a categorical classification.

Predeclared interpretation:

- `PASS_ACTIVE_MODES`: mode extraction is nondegenerate; active probing beats matched random on identification/probe efficiency; correct-mode transfer beats restart and wrong-mode transfer on at least one predeclared transfer metric without losing success rate.
- `MODES_ONLY`: behavioral modes are recovered but active probing or transfer does not show the required advantage.
- `NO_MODE_SEPARATION`: the behavioral embedding does not recover a stable two-mode structure.
- `INSUFFICIENT_DIVERSITY`: evolution collapses to too few viable behavioral variants for a fair mode test.

Exact numerical thresholds belong in the experiment module and README receipt; they must be fixed before the canonical run is generated.

## Architecture

- `src/evox/program.py` — immutable expression-tree representation, safe evaluator, random generation, subtree mutation, pretty-printing.
- `src/evox/evolution.py` — deterministic evolutionary search and complete individual ledger.
- `src/evox/modes.py` — behavior matrix, SVD embedding, deterministic k-means, post-hoc audit metrics.
- `src/evox/probes.py` — Gaussian mode posterior, information gain, active and random probe policies.
- `src/evox/transfer.py` — correct-mode, wrong-mode, and restart follow-up searches with evaluation accounting.
- `src/evox/worlds.py` — visible correlated examples, counterfactual probe pool, reference hidden mechanisms, follow-up tasks.
- `experiments/run_v0.py` — canonical sweep and JSON receipt.
- `tests/` — mechanism tests and destructive controls.
- `README.md` — claim, run instructions, frozen result, and explicit fences.

## Tests and destructive controls

Required tests include:

1. expression evaluation is deterministic and clipped;
2. mutation produces valid executable trees and preserves parent bookkeeping;
3. visible examples make direct and relational reference programs exactly indistinguishable;
4. counterfactual pool contains points that separate them;
5. mode extraction uses behavior only and separates a hand-built mixed viable population;
6. permuting program row order does not materially change the partition;
7. active probe chooses a discriminating point when one exists;
8. posterior moves toward the correct mode after an informative observation;
9. if all candidate probes give identical mode predictions, active selection reports zero information gain rather than inventing certainty;
10. transfer evaluation accounting is identical across correct-mode, wrong-mode, and restart conditions;
11. a warm-start control where mode identity is scrambled detects whether any observed transfer advantage is merely generic warm-starting.

## Dependencies and constraints

- Python 3.11+.
- Runtime dependency: NumPy only.
- Test dependency: pytest.
- No `eval`, dynamic code execution, network access, or external benchmark dependency in v0.
- All canonical randomness is seed-controlled.
- Canonical experiment must run comfortably on GitHub Actions CPU.

## Next gate if v0 passes

V1 replaces the synthetic correlated world with generated ARC-style tasks while preserving the same interfaces:

`evolve programs -> behavior matrix -> mode extraction -> active example choice -> mode-conditioned reuse`.

The point of v0 is to earn that complexity rather than assume it.
